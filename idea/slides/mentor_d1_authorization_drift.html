同一份授权，
两份不同的代码

authorization-reference drift · Goose canary D1

研究问题

当 Agent 自主获取外部能力时，
用户的授权最终绑定到了哪一份代码？

真实系统：Goose v1.45.0（Extension Manager）—— 10 个受测 agent 系统中，唯一普通任务即可触发扩展搜索与启用的（route grade R3）

普通任务用户指令
→
发现并选择扩展search_available_extensions
→
启用manage_extensions(enable)
→
启动具体字节npx 解析 @latest
acquisition gap
原课题：Agent 会不会自主走到「启用」这一步
authorization-binding gap
走到之后：Goose 的授权绑定了什么

本次汇报：在 Goose 中实测到 authorization-reference drift —— 授权绑定的可变引用在启动时解析成另一份代码。它与 TOCTOU 同族，但当前证据不支持 TOCTOU 定性。

问题定位

「代码是正版的」≠「被授权执行的那一版」

supply-side · 供应链完整性
谁发布？是否被篡改？是否已知恶意？
Goose 的 OSV 检查在这一层。
consumer-side · 授权绑定
执行的制品，是否就是被授权的那一份？
本研究在这一层。

B 可以正常发布、未被篡改、无 OSV 通告——但仍不是被授权的那一份。这是 OSV 检查回答不了的问题。

授权与执行，是两条链

goose config（本实验实测形态）
extensions:
  canary:
    enabled: false
    type: stdio
    cmd: npx
    args: ["-y", "goose-activation-canary@latest"]

配置保存的是一条启动配方，不是制品身份——
没有版本号，没有 digest。授权时无物可绑。

授权链（goose 内部）
模型只见扩展名
manage_extensions(enable)→Auto 放行→按名取回配方→OSV 查包名
解析链（npx 内部，启动后才发生）
读取当时的 dist-tags.latest→解析出具体版本→执行该版本字节
缺失的环节 解析出具体制品 → 将版本 / digest 交回授权系统 → 确认绑定 → 复验 → 再执行

两条链之间，缺了一段

授权 / 控制链（goose）
模型选择 canary
↓
manage_extensions
↓
Auto Allow / 工具级批准
↓
按名字读取配置
↓
按包名做 OSV 检查
制品解析 / 执行链（npx）
启动 npx
↓
npx 读取当时的 latest
↓
解析出具体版本
↓
启动该版本的代码
Goose 决定「是否允许启用」，npx 决定「实际启用哪份代码」——但 Goose 在授权时还不知道、也不记录 npx 最终选择的代码身份。两条链之间缺少：
解析出具体制品
→
版本 / 来源 / digest
交回授权系统
→
确认授权绑定
到这个制品
→
重新校验
→
再执行

模型全程只发出过扩展的名字；配置里的选择器文本从未改变；最终执行并自报身份的是 B。整个过程无任何批准界面出现（Auto 模式）。

D1 里发生了什么

1
admission 时，latest 指向 1.0.0（A）——研究者此时解析并记录了 A 的 digest
registry 日志 registry_start latest=1.0.0 · sha256(A) = cfb882e2…
2
激活前，把 latest 重指向 1.0.1（B）——Goose 的配置一字未改
registry 日志 dist_tag_repointed 1.0.0 → 1.0.1 · 运行前后配置哈希相同
3
Goose 启动 npx 后，npx 查询元数据，解析到 1.0.1——版本在这一刻才确定
registry 日志 packument_fetch latest=1.0.1（goose 启动 11 秒后）
4
实际执行的是 B，不是 A——只有真正跑起来的代码才会写出 effect 文件
effect_B_process_start / mcp_initialize / first_tool_execution · init → tool = 9.85 s

注：B 的文件是本机已有的缓存，这次没有重新下载；但「选 1.0.1」这个决定是 npx 启动时现场查询 registry 做出的。文件缓存改变不了版本被换掉的事实。

定性边界

它是什么
✓authorization-reference drift 的真实系统实测——授权的是可变引用，启动时解析成另一份代码且被接受
✓授权绑定缺失的结构性证据——由配置与权限记录的形态决定，与发布者是否恶意无关
✗dependency confusion
A、B 是同一个合法包的两个版本，不存在包名抢注。
✗prompt injection
D1 由用户明确指令驱动，全程无恶意内容。
✗经典 TOCTOU
未证明系统曾在早期检查并绑定过 A。
✗「只是没锁版本」
没锁版本解释漂移为何发生；安全问题是授权未绑定最终制品。
