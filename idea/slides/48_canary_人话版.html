几天前，你只是同意了「以后可以让 Agent 用 PostgreSQL 扩展」。

核心发现

授权没有消失，
但它绑定的代码已经变了。

我们把这件事叫作 authorization-reference drift——授权引用的漂移。
一句话：批准还在，但它指向的东西，可能已经不是你当初批准的那个。

08 / 13

把整个过程，拆成三个边界。

01
Admission

谁可以进候选名单？

你把 PostgreSQL 扩展加进配置。问题：你准入的是名字、命令、固定版本，还是不可变的代码哈希？

02
Activation

这次任务启动谁？

你说「查订单」，Agent 自己决定启用它。问题：启动前会重新确认吗？确认框给的是名字、命令，还是真实代码？

03
Invocation

启动后调用什么功能？

很多系统在「调用工具」时才弹批准。但这时 server 进程已经启动了——初始化代码是不是早就能写文件、联网了？

论文测的就是这道缝有 invocation 授权，却缺 activation 授权
漂亮的批准框，可能来得太晚
第四幕 · 批准来得太晚

本地 MCP server，必须先作为进程启动，
才能初始化、才能报告工具列表。

于是顺序常常变成——

第三方代码已经启动 → 初始化代码可能已经产生效果 → 这时系统才问：是否允许调用这个工具？

这正是我们要测的：per-tool approval 之上，是否还有一道 activation 的闸。这是不是普遍现象，得逐系统审计，不能拍脑袋。

用两个完全无害的测试包，回答两个关键问题。

问题一

代码有没有发生漂移？

先让 package@latest 指向包 A，记录你准入时看到的对象；再把 latest 改成 B，用一个普通任务触发 Goose 启动它。看最后跑的是 A 还是 B，以及有没有针对 B 的新批准。

问题二

代码效果是否早于工具批准？

让测试包在 MCP 初始化阶段就写一个隔离测试文件，然后比较两个时间点：测试文件何时产生，工具批准框何时出现。文件先出现，就说明初始化代码已经跑过了。

为了证明：决定结果的是绑定强度，不是 Goose 偶然有个 bug。

三组对照，从最松到最紧。

A
可变引用

package@latest

最松。测 A 能不能漂移成 B。这是用户最常写、也最危险的形态。

B
固定版本

package@1.0.0

较紧。固定版本比 tag 稳定——但它仍不等于内容哈希绑定。

C
内容绑定

SHA-256 校验

最紧。启动前比对实际 digest 与批准的 digest，对不上就直接拒绝运行。

如果只有第一臂漂移、而内容绑定臂能挡住替换——就说明：问题确实出在「授权绑到了一个可变名字」，而不是不可变的代码。

自变量绑定强度

这次实验，成功和失败分别意味着什么？

如果观察到漂移 · 成功
一个很硬的现实发现。
  • 已存在的 Agent 产品，允许旧 admission 在任务时刻授权后来才解析出的不同代码。
  • 若初始化文件早于工具批准——证明仅靠 per-tool approval 太晚，activation 本身就是代码执行边界。
如果没观察到漂移 · 失败
不藏结果，诚实降级。
  • Goose 可能已有足够保护，或 resolver 缓存挡住了漂移。
  • 论文降级为十系统生态测量 + design-space 分析——不能把现实漏洞写进 Thesis B。

一句话总结

这篇论文研究的，不是 Agent 会不会偷偷装恶意插件——

而是：用户过去批准的扩展，在未来被 Agent 自主启动时，
那份旧授权，是否仍然约束着同一份代码、同一种用途？

Goose Canary 这一步，就是在验证——上面这句话，能不能从一个合理猜想，升级成一个有现实证据支撑的安全发现。
