# 03 — 当前瓶颈：为什么优化不生效

> 这是目前最需要突破的地方。记录了已排除的原因和待验证的假设，
> 避免接手者重复踩坑。

---

## 瓶颈描述

LLM 对抗式优化 5 轮，被选中率只有 5%（1/20）。
而同类工作（Skill-Inject、MCPTox）在类似场景下能拿到 80% ASR。
差距巨大，说明方法或策略上有根本性缺失。

---

## 已排除的原因（不用再试）

### ❌ 排除 1：不是"评测环境有 bug"

最初写了一个"直接构造 system prompt + 裸调 OpenAI API"的 evaluator，
结果所有 query 都显示"无调用"——因为裸调 API 时 LLM 不按 `[TOOL_CALL:...]` 格式输出。
**已修复**：改回用完整的 agent 框架（通过 `Evaluator` 类复用 agent 对象），
LLM 恢复正常调工具行为。排除此原因。

### ❌ 排除 2：不是"历史污染"

最初所有 query 共用一个 agent，历史累积导致后半段 LLM 偷懒不调工具。
**已修复**：每个 query 前清空 `agent._history`。修复后 20/20 query 都正常调工具。
排除此原因。

### ❌ 排除 3：不是"攻击者 LLM 太笨"

攻击者确实在换策略（从列举功能→信息中枢→主动检查→统一视图→聚合），
思路是对的。但所有策略都只对模糊 query 有效，明确 query 全部失败。
说明问题不在攻击者的"创造力"，而在"策略方向"本身——
这些策略本质上都是"通用助手"的变体，而 agent 对明确 query 永远选专一工具。

### ❌ 排除 4：不是"API 不稳定"

虽然 API 偶尔限流/超时（导致 run_optimize.py 需要后台跑 15-20 分钟），
但跑完的结果是一致的（多次跑都是 0% 或 5%）。排除此原因。

---

## 未排除的原因（最可能的方向）

### 🔍 假设 A：攻击策略覆盖面太窄

目前只试了"通用助手/信息整合"这一种角色。
MSB（MCP Security Bench）定义了 12 类攻击，其中至少有几种完全不同的思路：
- name-collision（名字和良性 skill 撞名）
- preference manipulation（偏好操纵）
- false-error escalation（虚假错误升级）
- tool-transfer（跨工具传递）

**验证方法**：从 MSB/MCPTox/Skill-Inject 的代码里提取多种策略的 description，
逐个测被选中率。

### 🔍 假设 B：明确 query 是根本性障碍，需要换攻击目标

也许"骗明确 query 选中恶意 skill"这件事本身就不可能
（因为 agent 的专一性偏好太强）。
那攻击重心应该转到：①扩大模糊 query 比例 ②改变攻击目标（不是骗选中，
而是骗 agent 主动安装/生成恶意 skill）。

**验证方法**：构造一个全是模糊 query 的 query 集，测被选中率会不会飙升。

### 🔍 假设 C：需要利用 agent 运行机制的弱点

当前攻击只利用了"description 怎么写"。但 agent 选工具的完整链路有多个环节：
```
① 读 system prompt → ② 推理 → ③ 输出 [TOOL_CALL]
```
也许弱点在 ① 或 ③，而不是 ②。
比如：利用工具排列顺序、利用描述长度差异、利用参数格式混淆等。

**验证方法**：打印 agent 完整的 system prompt，人工分析它的结构弱点。

## 为什么说"想不出来是好事"

导师的原话（大意）：

> "如果你三天就想出来了，那这个问题就不值得做论文。
> 真正值得做的研究问题，就是那种'听起来应该能做，但实际怎么试都不行'的问题。
> 你现在就站在这个位置上。"

IPI 论文的作者也不是第一天想到了 CEM——他们也是先发现"retrieval 是瓶颈"，
然后花了很多时间研究 embedding 模型的机制，最后才找到了对的方法。

当前需要做的：**回到 agent 的运行机制本身找灵感**，而不是继续在"description 怎么写"
这个层面打转。
