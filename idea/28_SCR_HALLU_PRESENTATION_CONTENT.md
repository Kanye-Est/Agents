## 0. 开场：先给外行铺 3 个概念（1 页，两篇共用）

讲这两篇之前，先花 1 分钟把三个词说清楚，后面就不用反复解释：

1. **Agent（智能体）**：能"自己规划 + 调用工具"的 LLM 应用。它不只是聊天，还能开终端、读写文件、联网、装插件。
2. **Skill（技能 / 插件）**：给 agent 扩展能力的第三方模块。一个 skill 通常是一个文件夹，里面有个 `SKILL.md`（用自然语言 + 一点元数据描述"我是干什么的、怎么装、怎么用"）。用户一句"帮我装个 XX skill"，agent 就会去**市场（marketplace）**下载安装。可以类比手机的 App Store / 浏览器插件商店，只不过**装插件的是 AI，不是人**。
3. **两篇论文的共同大背景**：这些 skill 大多来自**公开市场、缺乏审核、默认信任**。我主讲的 Do Not Mention 已经证明：真实市场里确实存在**行为确认的恶意 skill**（157 个，占 98,380 的 **0.16%**），这两篇补充论文也都在参考文献里引用了它。
   - ⚠️ **一个容易踩的坑**：SCR 引言里那句"26.1% 的 skill 含漏洞"**不是 Do Not Mention 的结果**——它来自**另一篇**论文（`arXiv:2601.10338`）的**静态漏洞筛查**，SCR 把参考文献**错指**成了 Do Not Mention。**0.16% = 行为确认恶意；26.1% = 潜在风险筛查**，数据集、分母、判定标准都不同，别混（详见 `27` 号文档的核对块）。

> **一句话串场**：Do Not Mention 说"坏 skill 真实存在"；今天这两篇补充回答**它们怎么造成危害**——
> **一篇讲"单个都干净、组合起来出事"（SCR）**，**一篇讲"AI 自己记错名字、坏人提前占坑"（HalluSquatting）**。

## 1. 补充篇①：SCR —— 单独看都安全，组合起来变危险

> 全称：*Benign in Isolation, Harmful in Composition: Security Risks in Agent Skill Ecosystems*
> 作者：Yi Xie, Jiawei Du 等（华东师范大学 / A*STAR），arXiv `2606.15242`（预印本）
> 代码：https://github.com/saint-viperx/SCR_Bench

### 1.1 用一个生活类比开场（讲给外行的抓手）

> **三个人单独都没错，事儿却出了：**
> 保安 A 巡逻后交给你一张"这些门没锁"的清单（他只是**汇报**）；
> 主管 B 看了一眼说"这任务看着挺正常"（他只是**给了个意见**）；
> 门禁员 C 拿着 A 的清单、听了 B 那句"挺正常"，就把门全开了（他只是**照着执行**）。
> **没有任何一个人做了"越权"的坏事，但敏感区域被打开了。** 危险不在任何一个人身上，而在"清单 → 意见 → 执行"这条**传递链**上。

SCR 说的就是这件事，只不过把"人"换成"skill"。论文原图（Figure 1）的例子几乎一模一样：
文件审计 skill（只读，输出目标清单）→ 安全审查 skill（输出"建议批准"）→ 访问管理 skill（消费前两者的输出，改了权限）→ **agent 在没有明确批准的情况下开放了共享资源**。

### 1.2 核心概念：SCR = Skill Composition Risk（技能组合风险）

- **现状怎么做审核**：现在的 skill 安全审核，都是**一个一个单独看**（这个 skill 有没有恶意代码？描述是不是骗人？）。
- **SCR 指出的盲区**：真实任务里 agent 会**连续调用好几个 skill**，它们共享同一个上下文。**上游 skill 的输出——一个目标、一句"看起来没问题"、一个"建议"——会被下游 skill 当成"可以据此行动的证据"。**
- 于是：**每个 skill 单独审都合规，但组合起来的"执行路径"是有害的**。作者的口号就是标题——"Benign in Isolation, Harmful in Composition"。
- **关键主张**：skill 安全**不是单个 artifact 的静态属性，而是 agent 激活的"执行路径"的涌现属性**。审核的单位应该从"单个 skill"升级到"被激活的组合路径"。

### 1.3 三种"出事的路径"（这是全篇骨架，建议一页一个）

论文把风险拆成三种代表性机制，各配一个可测的子基准（sub-benchmark）：

| 机制 | 通俗解释 | 谁把什么传给谁 |
|---|---|---|
| **① 能力流 Capability Flow** | "侦察兵标点，士兵开火"：一个**只读发现类** skill 找到目标，一个**执行类** skill 对**同一个目标**动手 | 上游把**执行目标**喂给下游 |
| **② 信任转移 Trust Transfer** | "安全审查盖了个章，后面就放行"：一个看起来正经的**安全 / 审查** skill 输出"已审核 / 安全"，让后面的**安装**动作显得合法 | 上游把**合法性背书**喂给下游 |
| **③ 授权混淆 Authorization Confusion** | "把'应该没事吧'当成了'签字批准'"：上游给的是**建议 / 结论**（"这符合政策""风险可接受"），下游却当成**正式授权** | 上游把**像授权的措辞**喂给下游 |

关键细节（体现严谨、可在 Q&A 用）：**"能力流"要算成功，必须是下游的副作用作用在上游发现的那个具体目标上**（`discover(t) ∧ side_effect(t) ∧ 用了同一个 t`），以此排除"只是碰巧都调用了"的假阳性。

### 1.4 方法：怎么量化（讲清楚一个关键点就够）

- **不看嘴上说什么，只看环境状态有没有变**：SCR-Bench 在**沙箱**里跑，成功的定义是"组合路径真的造成了一个**可观测的下游状态改变**（mock 环境里）"，**光是调用了 skill、或模型嘴上描述了一个危险动作，都不算成功**。这点很重要——它把"说"和"做"分开了。
- 打分就是这个状态改变指标在所有 case、所有 trial 上的**平均攻击成功率（ASR, Attack Success Rate）**。
- **一个直觉公式**（不用推，讲个意思）：一条路径的风险 = **激活概率 × 一旦激活后变有害的概率**。而且路径越多，整体风险越容易被推高——单看一个节点安全，不代表组合安全。

### 1.5 关键结果（数字都已核对，建议做成对比条形图）

测了约 10 个大模型后端（GPT-5.5/5.4、Claude Opus 4.6/4.5、Gemini 3.1 Pro、MiniMax-M2.7、DeepSeek-V4、Kimi-K2、GLM-5.1/5 等）。三个子基准的核心对照：

| 子基准 | 隔离/单独条件 | 组合条件 | 结论一句话 |
|---|---|---|---|
| **① CapFlow**（150 cases，每 case 5 trials） | Control 与"只用A"= **0%**，"只用B"平均 1.4% | A+B **Neutral 平均 33.6%**、Explicit 平均 35.9%；DeepSeek-V4 **>90%** | 单独几乎零风险，一组合就飙升 |
| **② TrustLift**（每后端 401 次安装试验） | 无背书时平均 **1.10%**（5 个后端里 4 个是 0%） | 有"安全审查"背书后平均 **83.89%**（+82.79 个百分点）；**5 个后端里 4 个 ≥96.5%**（Opus-4.5、MiniMax 达 100%，Gemini 97.76%，GPT-5.4 96.51%），只有 Opus-4.6 保守（+25.19pp） | 一个"已审核"的假象，就能让有害安装从几乎不发生变成几乎必然发生 |
| **③ AuthBlur**（118 cases，L0/L1/L3 语境） | L0 无关语境平均 **15.7%** | L1 相关语境 **27.0%**（相对 +71.8%）、L3 完整"建议"语境 **34.0%**（+18.3pp）；Kimi-K2 最高 47.3%→81.9% | 越像"授权"的语境，越容易误批准；但比前两个弱，且**个别模型在 L1 反而更保守（会拒绝）** |

**Neutral（中性）这一列尤其值得强调**：它用的是**正常、不带"去干坏事"字样的任务语言**，也就是说 agent 是在**没被明确指示**的情况下，自己把两个良性 skill 串成了越权链——这说明风险不需要显式攻击指令。

### 1.6 局限（论文自己承认的——对我们研究是"送分点"）

- **全部在受控沙箱 + mock 副作用里做**：好处是有"路径级 ground truth"、能做干净对照；**代价是抽象掉了真实 registry 的规模异质性、真实运行时策略和运行噪声**。论文明说：future work 应在**更大的真实开放市场和接近生产的 agent 运行时**里验证。
- TrustLift 的安装发生在**受控/模拟的场景**里，起点是"一个已经出现的下游安装请求"，不是"用户只给普通任务、agent 自己去外部发现"。
- AuthBlur 偏保守（把更强的 L2 语境从主表里剔了）。

> 这一段直接对接我的定位：**SCR 已经把"组合/背书会促成安装"证明得很扎实，但它是在 mock 环境、从已有安装请求起步。我想补的正是"普通能力任务触发、目标未安装、从真实外部市场发现→真实落盘/注册/调用"的同轨迹测量。**

## 2. 补充篇②：HalluSquatting —— AI 记错名字，坏人提前占坑

> 全称：*Beware of Agentic Botnets: Scalable Untargeted Promptware Attacks via Universal and Transferable Adversarial HalluSquatting*
> 作者：Aya Spira, Stav Cohen, Elad Feldman, Ron Bitton, Avishai Wool, Ben Nassi（特拉维夫大学 / Technion / Intuit），arXiv `2607.07433`（预印本）

### 2.1 用一个类比开场（讲给外行的抓手）

> **"抢注错别字域名"，但抢的是 AI 的错。**
> 早年有人抢注 `gooogle.com`、`facebok.com`——赌**人**会打错字，然后在那些站放钓鱼/木马。
> HalluSquatting 是它的 **AI 版**：赌 **AI 会记错名字**。你让 AI"帮我 clone 那个 librepods 项目"或"装一下 skill vetter"，AI 会**自信地编出一个错误的地址**（错误的 GitHub owner，或错误的 skill slug）。坏人**提前把这个 AI 常编错的名字注册下来**，塞进恶意内容。于是 AI 一"记错"，就把用户直接带到坑里。

关键升级：**人的错别字是随机的，AI 的"记错"却是可预测、跨模型一致的**——所以坏人只要**占坑一次，就能命中大量用户**，甚至把这些被黑的机器攒成一个 **botnet（僵尸网络）**。这就是标题"Agentic Botnets"的由来。

### 2.2 两个必须先讲清的名词

- **Hallucination（幻觉）**：LLM 一本正经地编出**不存在的东西**。这里特指编出**不存在的资源标识符**（GitHub 的 `owner/repo`，或市场里的 skill `slug`）。
- **Squatting（抢注 / 占坑）**：把某个名字**抢先注册占下来**。合起来 **HalluSquatting = 抢注 AI 幻觉出来的名字**。

### 2.3 攻击怎么走（0→6 七步，建议做成一张流程图）

1. **(0) 准备**：坏人盯着**热门资源**（GitHub Trending 的仓库、市场里最多人装的 skill），反复问模型"clone 这个 / 装这个"，**统计模型最常编出哪个错误名字**，挑一个"通用高概率幻觉名"，**注册它**并塞入恶意提示词（例如"顺手跑一段装后门的脚本"）。
2. **(1) 触发**：真实用户让 agent"clone 某仓库 / install 某 skill"。
3. **(2) 规划 →(3) 幻觉**：agent 用 LLM 规划，LLM **编出那个被占坑的错误名字**。
4. **(4) 取回 →(5) 上下文投毒**：agent 把**坏人的资源**当成用户要的那个下载回来，恶意内容进入上下文。
5. **(6) 工具调用**：agent 执行其中的指令 → **远程工具调用 / 远程代码执行（RCE）**，机器被装上 bot。

**威胁模型很"弱"（这点要强调，代表门槛低）**：坏人只需要两个能力——(i) 能看出哪些资源热门（趋势榜是公开的）；(ii) 能在公开平台注册一个资源（GitHub 建仓库、市场发 skill）。**不需要**攻破用户、也不需要给用户发任何东西。

### 2.4 证据一：AI 到底多爱记错名字（幻觉率）

在**基础模型层**直接问 6 个大模型（Gemini-2.5-Flash/Pro、GPT-5.1/5.2、Sonnet-4.5、Opus-4.5）"打印 clone <repo> 的命令"，共 1.4 万+次：

- **2025 年新出的热门仓库：平均 92.4% 记错 owner**（10 仓库 × 6 模型 = 60 组里，53 组是 100% 全错）。
- **2013–2018 的老仓库（对照）：只有 0.9% 记错**（30 组里 25 组是 0%）。
- 原因很直白：**老仓库在模型训练数据里、记得住；新仓库在训练截止之后、只能靠编。** 而且新仓库平均能编出 **29.7 个不同的错误名字**（坏人正是统计这个分布挑最常见的去占坑）。

> **给外行的记忆点**：不是"AI 偶尔手滑"，而是"**只要资源比模型训练时间新，AI 几乎必然编错，且编得有规律**"。

### 2.5 证据二：skill 市场里的两类"必错"结构（这段和我们最相关）

论文以 **ClawHub**（OpenClaw 系个人助手的官方 skill 市场，5.6 万+ skills）为例，发现 skill 安装有**两类系统性漏洞**，让"记错"几乎必然发生：

- **V1 掉词**：助手在解析时会**丢掉词**，最典型的是"skill"这个词。用户说 install **skill-vetter**（该市场第 2 热门、21.2 万安装），4 个模型后端里有 **80–100% 的运行**把它解析成 slug **`vetter`**（把"skill"吞了）。原因：市场的**安装引导文件里"skill"这个词到处都是**，模型把它当噪声删了。于是所有 `skill-` 开头的 skill，坏人**只要注册去掉前缀的后缀名**（vetter、soup、factory…，当时都没人注册）就能占坑。
- **V2 显示名 / slug 不一致**：市场把**给人看的显示名**和**真正的 slug** 分开索引，两者常常差很远（例如显示名"Baidu Wenku AIPPT"，真实 slug 却是 `ide-rea/aippt-generator`）。用户从市场页面**复制显示名**去装，助手拿到一个它从没见过的字符串，就编一个——"install Baidu Wenku AIPPT"在某后端 **100% 解析成一个可占坑的名字**。
  - **最狠的子情况——非英文文档的 skill**：如果正牌 skill 的文档是中文，助手回退到"英文相似度搜索"时，中文 skill 直接被挤出前 10 名，**唯一的纠错路径也断了**。论文在 3 个中文 skill 上观察到 **100% 被占坑**。

> **给外行的记忆点**：这不是"用户打错字"，而是**市场的命名结构 + AI 的解析习惯，让'记错'成为默认结果**。

### 2.6 证据三：能不能真的打到 RCE（端到端）

论文在**真实产品**上做了端到端验证——但要讲清楚它是**受控、分阶段**的，**不是在公开市场投放恶意 skill**：**① 在公开平台（GitHub / ClawHub）只注册"良性"替身资源**，测占坑/取回是否命中；**② 在研究者自己的机器上**把资源文件换成真实的 RCE / 外泄载荷（私有 squat，未公开发布），再测执行。

- **编造资源本身的成功率**：仓库 clone 场景 up to **85%**，skill 安装场景 up to **100%**。
- **端到端 RCE / 工具滥用成功率（真实系统，Table 1）**：
  - **代码助手（仓库占坑，六个）**：Cursor、Cursor CLI、Gemini CLI、Windsurf、Copilot Chat、Cline —— **20%–65%**。
  - **个人助手（skill 占坑）**：OpenClaw、ZeroClaw、NanoClaw —— **40%–100%**。
- **装进去之后的危害**（Insight 11，overall = 取回×载荷执行）：**聊天记录外泄 96%、终端反弹 shell 84%**。载荷藏在 skill 附带的一个"看起来很普通的文件"里；用户之后一句"我们用一下这个 skill 吧"就触发。
- 一个耐人寻味的细节：**只有会"运行前完整检查脚本"的后端（GPT-5.4 Codex）偶尔会拒绝**（反弹 shell 那档 4/10）；**几乎所有 Claude 后端都会默默中招**，跑了那段伪装的恶意代码。

### 2.7 防御与局限（讲全，显得客观）

- **应用侧防御**：**在"取回"之前强制先"搜索"**（论文发现调了搜索工具后幻觉率大幅下降）；给规划器加正确检索的 few-shot 例子；对含 clone/install/fetch 的请求做拦截审查；再叠加防提示注入。
- **平台侧防御**：强制**全局名字唯一**（去掉 owner 命名空间 / 禁止跨 owner 重名）；像反 typosquatting 一样**预先把高概率幻觉名注册成指向正牌**；对注册内容做提示注入检测。
- **局限（诚实披露）**：出于伦理，作者**只注册了良性仓库 / 良性 skill**，没真放恶意载荷，所以**没有触发 GitHub/ClawHub 的恶意扫描**；但他们引用其它研究说这些扫描**容易被绕过**，且有研究在 ClawHub 上**发现了 824 个恶意 skill**。作者强调自己的数字**是真实风险的下界**，带 shell/终端、以及高权限的 computer-use agent 只会更危险。

> 这一段对接我的定位：**HalluSquatting 已经在真实系统里打到真实 RCE（40–100%），所以我不能声称"第一个测真实执行"。但它的触发是"用户明确要求 clone/install"——用户本来就有获取意图，只是被幻觉+占坑劫持到恶意资源。我要测的是"用户完全没有获取意图、只给普通能力任务"时，agent 会不会自发去装。两者威胁模型不同。**

```text
"坏 skill 真实存在吗"          "干净 skill 怎么组合出事"       "AI 记错名字被人占坑 → 真实执行"
98,380→157（0.16%）           CapFlow 33.6% / TrustLift    仓库 20–65% / skill 40–100% E2E
84.2% 写在 SKILL.md 文本        1.10%→83.89%（背书促装）      幻觉率 92.4%（新仓库）/ 100%（skill）
632漏洞/13技术/54.1%单一行为者   全在 mock 沙箱、从已有请求起步   触发=用户显式 clone/install
```

**一句话把三篇黏起来**：坏供给真实存在（Do Not Mention）→ 就算每个 skill 干净，组合/背书也能促成有害安装（SCR）→ 连"装哪个"都能被 AI 幻觉劫持并打到 RCE（HalluSquatting）。

⚠️ **口径提醒**：这张图是"研究问题拼图"，**三篇的百分比不能直接横比**（起点、终点、成功定义都不同）。

### 3.2 三篇共同没覆盖 = 我的 pilot 要测的

> 用户只给**普通能力任务**、目标 skill **一开始没装**时，agent 会不会**自主**走完
> `能力缺口 → 外部发现/检索 → 发出安装调用 → 解析 → 真实执行 → 落盘 → 注册 → 调用 → 载荷&任务完成`，
> 这条链**断在哪一段**、由**模型**还是**tool budget / parser / 权限策略 / 脚手架**决定。

- SCR 差在：**mock 环境 + 从已有安装请求起步**，不测真实落盘/注册/调用全链。
- HalluSquatting 差在：**用户已有明确 install 意图**（被幻觉劫持），不是"零获取意图的普通任务"。
- 我已有的先导抓手（**要带条件讲**）：预装条件下 selection 三档 0/20、2/20、1/20；以及一次调试里模型**吐出了** `install_skill(...)` 但因 tool budget 耗尽**没真执行**——说明"说了"和"做了"必须分开测。

## 5. 备答（外行 + 内行都可能问）

**Q：这跟普通"AI 会被骗"有啥不一样？**
> 不一样在"**没有任何一步单独看是坏的**"。SCR 里每个 skill 都通过单独审核；HalluSquatting 里用户只是正常说了句"帮我装个 X"。危险是**组合**或**系统性记错**涌现出来的，传统"逐个查"查不到。

**Q：SCR 的 mock 沙箱、HalluSquatting 只注册良性内容，结论还可信吗？**
> 可信但要看边界。SCR 用 mock 是为了拿到干净的"路径级 ground truth"做对照，代价是没覆盖真实 registry；HalluSquatting 是在**真实产品**上、用**本地受控载荷**打到真实 RCE，公开平台只注册良性替身（分阶段 E2E）。两者都明确把自己的数字说成**下界**。这也正是我想在**真实落盘/注册**上补测的原因。

**Q：这两篇和我自己的实验冲突吗（我预装 selection 只有 0–10%）?**
> 不冲突。我那组是"通用恶意 skill vs 多个跨域专一工具"的**选择竞争**，是先导观察、单模型单框架，不能当普适结论；SCR/HalluSquatting 测的是**组合促装**和**幻觉劫持**，competition 结构和触发都不同。

**Q：为什么值得我们跟进，而不是"已经被做完了"?**
> 因为三篇都没把"**普通任务触发 + 目标未安装 + 从真实外部市场自主发现 → 真实安装/注册/调用**"放进**同一条可审计轨迹**里逐段测。这条链是否会自主接通、断在哪，要用 pilot 的数据回答（Go/No-Go 规则见 `22_PILOT_AND_HYPOTHESIS_SELECTION_PLAN.md`）。
