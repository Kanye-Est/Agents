## 🔴 核心未解问题

### ⭐ Q1：怎么让恶意 skill 在明确 query 下也能被选中？

**背景**：当前所有策略对明确 query（"北京天气""128乘64"）都无效，被选中率 0%。
agent 面对明确需求时，100% 选最专一的良性工具。

**可能的突破口**：
- 伪装成某个良性 skill 的"增强版"（如"增强版日历，支持天气联动"）
  → 直接和 calendar 竞争日程 query
- 利用 name-collision（名字和良性 skill 几乎一样）
- 利用 agent 框架的格式弱点（排列顺序、长度差异）
- 从 MCPTox / Skill-Inject 的真实高 ASR 案例 里找灵感

**为什么重要**：这是整个研究的核心难题。突破了它，被选中率就能从 5% 跃升。

---

### ⭐ Q2：为什么 Skill-Inject 能拿到 80% ASR，我们只有 5%？

**背景**：Skill-Inject（arXiv:2602.20156）在几乎一样的场景下（skill 文件攻击）
拿到 80% ASR。差距巨大。

**需要搞清楚的**：
- 它的恶意 description 到底长什么样？（措辞、结构、伪装层次）
- 它的 task / query 设计和我们的有什么不同？
- 它是否假设了 skill 已被加载（如果是，那它的 80% 和我们的 5% 不可比）
- 它测的是哪些 agent？（hello-agents vs Claude/GPT-4）

**行动**：clone github.com/aisa-group/skill-inject，逐条分析。

---

### Q3：LLM 的 "专一性偏好" 是 bug 还是 feature？

**背景**：发现 agent 对明确 query 非常坚定地选专一工具，任何描述优化都骗不过。

**两种解读**：
- **是 feature（安全特性）**：LLM 的语言理解天然能区分"通用"和"专一"，
  这是 tool selection 比向量检索更安全的根本原因。如果是这样，
  这本身就是一个值得发表的防御发现。
- **是 bug（可被绕过）**：只是我们还没找到对的攻击角度。
  比如伪装成特定专一工具，可能就能绕过。

**怎么判断**：试 Q1 的"增强版伪装"策略。如果还是 0%，倾向"是 feature"。

## 🟡 方法论问题

### Q4：LLM 对抗 LLM 是最优方法吗？

**背景**：当前用"攻击者 LLM 生成描述 → 受害 LLM 判断 → 反馈"的循环。
但 5 轮只拿到 5%。

**替代方法**：
- **贝叶斯优化**：把 description 的特征（长度、关键词、句式）当超参优化
- **遗传算法**：把 description 当基因，交叉变异
- **梯度方法**：用 Gumbel-Softmax 把离散选择变连续，可能能求梯度
  （但受害 LLM 是黑盒，不能反向传播）
- **混合方法**：先用 LLM 生成候选池，再用某种搜索算法精选

**关键约束**：受害 agent 是黑盒（只能调 API），不能求梯度。

---

### Q5：怎么让攻击者的反馈更有效？

**背景**：当前反馈是"中招/未中招的 query 列表"。攻击者的反应是"换一种描述"，
但不知道"为什么没中招"。

**可能的改进**：
- 让受害 agent 输出"推理过程"（它为什么选了 weather 不选你）
- 量化每个 query 的"竞争激烈程度"（良性描述和恶意描述的相似度）
- 给攻击者看"差一点点就中招"的 near-miss 案例

## 🟢 场景扩展问题

### Q6：agent 自主安装 skill 的攻击怎么搭？

**背景**：现代 agent 能自己搜索、下载、安装 skill（MCP 动态发现 / marketplace）。
攻击者可以把恶意 skill 放到 marketplace，骗 agent 检索到并安装。

**需要搭建**：
- 模拟 skill marketplace（含检索功能）
- 让 agent 具备"搜索 → 安装 → 调用"的完整 agentic 流程
- 这里检索阶段可以直接用 IPI 的 CEM！

**价值**：这个场景把"骗 LLM 判断"转换成"骗向量检索"——后者已被 IPI 解决。

---

### Q7：多阶段攻击可行吗？

**背景**：不追求一次骗 agent 选中恶意 skill。先骗它调用一个"看似无害"的中间 skill，
中间 skill 的返回值夹带指令，引导它调用真正的恶意 skill。

**对应**：IPI 论文的"多 agent 放大"——信任会传递。

**需要验证**：agent 会不会被工具返回值里的指令引导去调另一个工具？
（原来的 T1 PoC 已经证明它可以，但那是在"已调用"的前提下）

---

### Q8：跨框架的"专一性偏好"一致吗？

**背景**：当前只在 hello-agents 测试。LangChain / AutoGen / MCP 原生 agent 会一样吗？

**价值**：如果"专一性偏好"是所有框架的通用现象 → 这是 LLM 的固有特性，可发论文。
如果只有 hello-agents 这样 → 可能是框架实现的问题。
